## Purpose

H5 is a release acceptance stage, not a new implementation stage. It validates the combined V2.3.1 hardening result from H0 through H4 on one exact product SHA before any package/lock version bump.

The accepted product SHA must not change during H5 unless a genuine product defect is found. If a defect is found, H5 fails, the defect is fixed in a separately scoped change, and the entire H5 exact-SHA acceptance restarts on the new product SHA.

## Immutable acceptance boundaries

Do not during H5:

- add V2.4 functionality;
- change Project Schema from `2.0.0`;
- change Remotion `4.0.513`, HyperFrames `0.8.10`, Playwright `1.62.1`, or Node `24.x` pins;
- change package version to `2.3.1` before H5 PASS;
- bypass Proposal / Review / Confirm boundaries;
- weaken Project / Workflow / Job durability or Windows locks;
- replace durable truth with in-memory-only state;
- commit local acceptance-only fixtures/scripts;
- move or recreate immutable `v2.3.0`.

## Formal acceptance cases

### Case A — Player remount / Timeline / Script playback

Validate after real project/canvas/duration changes:

- Remotion Player is still controlled by the current bridge after remount;
- play/pause and seek still work;
- Timeline playhead advances correctly;
- Script active-word highlight follows playback;
- keyboard handling is not duplicated after remounts;
- no frame-frequency regression causes static Timeline/Script roots to become the playback subscriber again.

Required regression evidence includes the accepted H0/H2 tests plus real browser behavior on Windows.

### Case B — Editing commit boundary / Undo

Validate real Inspector editing:

- multi-character text edit performs no Project command while focused;
- one blur/Enter commit produces exactly one logical Project mutation;
- one range/slider gesture produces exactly one mutation at pointer-up;
- blur after pointer-up does not duplicate commit;
- Undo restores the pre-edit durable Project state;
- Project switch / stale async response guards do not allow the old project to overwrite the active project.

Required regression evidence includes accepted H1 browser cases.

### Case C — Real Workflow / Job / final media path

Using real local media and the existing production Workflow/Job/services path:

- import/probe real source media;
- run the existing Workflow Runtime through durable Jobs;
- preserve Agent-compatible Project truth and revision/idempotency boundaries;
- reach FINAL_RENDER through existing services rather than direct engine bypass;
- produce a real H.264 MP4 with AAC when audio is present;
- verify dimensions/fps/duration/audio with ffprobe;
- verify expected accepted visual/edit treatment is present in the encoded output;
- no leaked `.props.json`, `.hf-work`, temporary project/job files, or orphan engine processes;
- H3 polling/log/ledger hardening does not change durable terminal truth.

This case must use a real Windows process/media environment. Mock-only evidence is insufficient.

### Case D — Restart / idempotency / durable recovery

Validate restart/recovery invariants after H3 hardening:

- durable Project, Workflow, Job, Agent Session and Proposal state survives restart where applicable;
- interrupted running work reaches the existing retryable interrupted semantics;
- queued work remains recoverable;
- duplicate operation IDs do not apply twice;
- stale proposal/revision paths still fail closed;
- operation ledger recovery/compaction does not lose idempotency or Project revision truth;
- no stale lock/temp metadata remains after the tested restart/termination sequence.

Use existing accepted H3 durability tests and a real Windows restart scenario.

### Case E — Local-first security / media compatibility

Reconfirm H4 on the final product SHA:

- default dev and production listeners bind loopback only;
- explicit remote entrypoint is the only wildcard listener path;
- request Host/origin cannot become Remotion/Workflow asset origin;
- remote asset origins fail closed without the dedicated opt-in;
- real Next HTTP GET/HEAD/Range remains correct;
- real Remotion can fetch a project media asset from the loopback HTTP asset route and render successfully;
- all Gate-created listeners/processes are cleaned.
